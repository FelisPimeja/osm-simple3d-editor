# OSM Simple 3D Editor — план

Браузерный редактор 3D-атрибутов зданий OSM (схема Simple 3D Buildings).
Без бэкенда, хостинг на GitHub Pages.

## Архитектура

- **Карта:** MapLibre GL + векторные тайлы OpenFreeMap (подложка; здания тайлов — только ниже z15 и пока не загружены свои).
- **Здания:** на z ≥ 15 — свои данные по тайлам z14 (`src/view/overpass-tiles.ts`): память (LRU) → IndexedDB
  (`src/view/tile-store.ts`, своя база на сервер) → сеть. Источник — OSM API `/map` того сервера, куда идёт запись
  (дробление на четверти при 400, неполные мультиполигоны — через `/full`), не больше двух запросов сразу (правила
  OSMF для API). Overpass с 2026-10-09 не используется (раньше — пул overpass-api.de / maps.mail.ru).
  Неполные ответы не кешируются; в индикаторе — источник и возраст тайлов, кнопка «Перезагрузить видимые тайлы».
- **Рендер:** three.js custom layer (`BuildingsLayer`), одна слитая геометрия на тайл, цвет и выделение в вершинах,
  крыши (в т.ч. straight skeleton в worker), плоские следы для контуров с частями и зданий нулевой высоты,
  оверлей поверх всего (`depthTest: false`) для подсветки выбираемого контура.
- **Правки:** единый режим — правки (`EditSession`) лежат поверх тайлов (оверлей подменяет объекты в тайлах),
  объекты начинают отслеживаться при первой правке. Можно создавать отношения `type=building` и менять их членов.
- **Геометрия и топология** (решение 2026-10-11): в OSM — простые замкнутые пути, связность — общими узлами,
  а не мультиполигонами из общих отрезков. Мультиполигон создаём только по необходимости: часть с дырами,
  контур здания из несвязанных частей. Чужие мультиполигоны и общие пути не перестраиваем и не «упрощаем» —
  правим, сохраняя их структуру (`restructureRing` в `src/edit/topology.ts`). Связность («ребро → чьё», «узел →
  чьи пути») строится в памяти из загруженных данных и служит всем инструментам (привязки, перемещение,
  вытягивание, разрезание, отделение от соседей). Почему не мультиполигоны: так принято в OSM (мультиполигон —
  когда путём не обойтись), пути без тегов в нескольких отношениях легко ломаются в iD/JOSM, каждая правка
  задевала бы много объектов; отделить часть от соседей на узлах — просто заменить общие узлы новыми.
  Части друг над другом с одним основанием — тоже два пути на одних узлах, без общего пути.
- **Запись:** OAuth 2.0 PKCE → свежие версии из API (`fetchElements`) → перенос правок (rebase тегов, слияние членов)
  → `changeset/create` → `upload` (osmChange `<create>`/`<modify>`) → `close`; записанное сразу попадает в кеш тайлов.
  Сервер по умолчанию — боевой, dev — по выбору.

### Indoor и планы этажей

- [ ] Подумать над глобальным отделением поэтажных планов от конкретных зданий. В схеме Simple Indoor Tagging привязки планов к зданиям нет, и, возможно, её не нужно придумывать: от эвристик привязки (по геометрии, комплексы без здания, якорь комплекса) местами вылезают неочевидные проблемы. Связано с пунктом про постоянный ключ комплекса ниже.
- [ ] Отметка пола первого (нулевого) этажа. В indoor-схеме отметки нет: сейчас она выводится из `min_height` частей с `building:levels` (пример — relation/21812732: пол этажа 0 на 0,7 м над цоколем). Остальные этажи по идее выводятся из неё и высот этажей (`height` на `indoor=level`).
- [ ] Поэтажный план: перестраивать после правки только изменённые стены и то, что с ними соприкасается, а не весь этаж. Сейчас любая правка тегов (например, `height` у 12 стен Казанского вокзала, relation/3662125, этаж 0) перестраивает план целиком: ~0,75 с на 1500 объектов. Сложность: план строится одним проходом, стены зависят друг от друга — стыки и вертикальные рёбра, совпадающие грани (`uncovered`), проёмы дверей, цвет граней по помещениям, крышки под кровлей. Нужен кеш по кускам (например, по ячейкам сетки) с пересборкой затронутых ячеек и их соседей.
- [ ] Постоянный ключ комплекса indoor без здания. Сейчас (`complexAnchor` в src/main.ts) это самый старый объект OSM комплекса: отношение с наименьшим id, иначе путь, иначе точка. Работает, но многоступенчатый выбор неочевиден, и ключ меняется, если удалить сам якорь. Связано с URL плана без здания.
- [ ] Хвосты инструментов планов: «Объединить» — мультиполигоны, объединение с дырой внутри, пути в составе отношений (сейчас отказ); «Точка» — двери на стенах-линиях `indoor=wall` и в мультиполигонах, значок у точки без вида; «Повторять на этажах» — копирование стен-линий и мультиполигонов из нескольких частей, правка `level` галками в «Свойствах»; трассировка — пересечения рёбер как узлы, клавиша «другая сторона», трассировка в «Рассечь».
- [ ] Эскалаторы, лестницы и пандусы на планах: визуально проверить примеры на карте, доработать лестницы и пандусы.
- [ ] Читать `min_level` / `max_level` / `non_existent_levels` с контура или отношения здания (вики велит ставить их при сочетании со Simple 3D; сейчас не читаются).
- [ ] Обсудить на форуме (при необходимости — Proposal) тегирование подземных объёмов на разных уровнях: `building:levels:underground` задаёт только число этажей от земли, ключа начального подземного уровня нет, отрицательные `min_height` и `building:min_level` не закреплены. До решения новых тегов не вводить; обходной путь — indoor-разметка.

### Крыши и геометрия зданий

- [ ] Пересечения граней (а не только рёбер) частей здания: ребро одной части протыкает грань другой, грань пересекает грань. Нужно для привязок (сейчас `intersection` — только пересечения рёбер, src/render/edge-intersections.ts) и, возможно, для рёбер на линиях пересечения кровель соседних частей.
- [ ] Предупреждения о непокрытой площади у нависающих крыш и несовпадения стыков крыш на нерегулярных контурах ([wolfbert, №11](https://community.openstreetmap.org/t/148767/11)); нужны примеры.
- [ ] Эксперимент: `side_hipped` на основе вальмового скелета (стратегия [Zkir, №69](https://community.openstreetmap.org/t/148767/69); пример — хор St. Oswald, [way/780970072](https://www.openstreetmap.org/way/780970072), [relation/10828887](https://www.openstreetmap.org/relation/10828887)). Построить вальмовую основу, по `roof:direction` найти торцевое ребро, заменить его скат вертикальным фронтоном и продлить соседние скаты. Сначала — выпуклые контуры без дыр с однозначным торцом; критерии отказа (почти квадрат, равнозначные рёбра, многосегментный торец); отдельной веткой, не меняя обычный `hipped`; проверить также вариант разметки хора `gabled` + `apse_gabled`. По результату ответить Zkir.
- [ ] Изучить [ProposedRoofLines](https://wiki.openstreetmap.org/wiki/ProposedRoofLines) (`roof:ridge`, `roof:edge`, `roof:apex`, роли `ridge`/`edge`): чтение, построение, затем правка. Исследование без сроков.
- [ ] `quadruple_saltbox` на невыпуклых контурах даёт неправдоподобные скаты над террасами ([Zkir, №43](https://community.openstreetmap.org/t/148767/43)): ограничить выпуклыми контурами или четырёхугольниками.
- [ ] `dropCollinear` упрощает контур для скелета крыши (излом до 12°, отклонение до 0,5 м), почти плоская вставка рядом с крутыми скатами выглядит как щель ([issue 39](https://github.com/FelisPimeja/osm-simple3d-editor/issues/39), way/579925214). Оценить `COLLINEAR_DIST` 0,15–0,2 м: устойчивость скелета на изогнутых зданиях и время.
- [ ] Примеры [MaestroGlanz, №34](https://community.openstreetmap.org/t/148767/34): [первый](https://felispimeja.github.io/osm-simple3d-editor/?server=osm#18.38/47.869739/12.647845/13.6/57) (противоречие `height=6` / `min_height=48` — проверить отображение и диагностику), две крыши церкви южнее него (несуществующее значение формы), [второй](https://felispimeja.github.io/osm-simple3d-editor/?server=osm#19.73/48.0056491/10.178316/-56/52) (причина не установлена).
- [ ] Вычитание как исправление в «Проверке»: части перекрываются по объёму → «Вырезать из …» (`polygonClipping.difference` по контуру меньшей части), только при однозначном результате.
- [ ] Автоисправление «Часть здания вне контура» (`orphan-part`), отложено: контур-объединение соприкасающихся частей + отношение type=building. Открыто: какие теги переносить на контур, части с building=* и building:part одновременно (relation/7259821), пристройки без адреса.

### Интерфейс

- [ ] Перекомпоновать панель инструментов (группировка, порядок, поиск действия) и иконки в единой стилистике, согласованные с названиями, подсказками и клавишами; перегенерировать иконки форм крыш.
- [ ] Пересмотреть панели: проверка вмещает мало ошибок, свойства меняют положение/заменяют проверку при выделении, список правок занимает место до отправки ([jnpoJuwan, №36](https://community.openstreetmap.org/t/148767/36)).
- [ ] Тулбар кнопок панелей правой колонки: включать и выключать показ отдельных панелей (слои, проверка, правки, части здания, этажи). Позволит добавлять новые панели, не перегружая колонку, и разгрузить мобильный интерфейс, выключив то, что сейчас не нужно. Кнопку слоёв убрали: слои пока — постоянная панель.
- [ ] Включение и отключение отдельных проверок валидатора (в том числе об отсутствии `type=building`), сохранять между сессиями ([ivanbranco, №61](https://community.openstreetmap.org/t/148767/61)).
- [ ] Настройка стилей отображения: панель или выбор из пресетов.
- [ ] Оверлей полноты разметки зданий: выделять отсутствие этажности/высоты и других тегов, как оверлеи StreetComplete.
- [ ] Панель фильтров объектов: выборки по тегам, типу объекта и геометрии (здание, часть, вход, узел, линия, полигон) с подсветкой результата заданным цветом (несколько фильтров — несколько цветов) и переходом по списку найденного. Запрос — в SQL-подобном синтаксисе (`building=apartments AND NOT has(entrance)`, `building:levels IS NOT NULL AND height IS NULL`) плюс простой визуальный конструктор условий; сохранять фильтры между сессиями. Нужны связи: «здание без входов», «вход жилого дома» — по узлам контура. Сценарии проверки: здания с этажностью, но без высоты в метрах; здания без `roof:shape`; жилые дома без входов; входы жилых домов без `ref` и `addr:flats`. Связать с оверлеем полноты выше.
- [ ] Кнопка × над масштабированием для возврата к карте ([MaestroGlanz, №34](https://community.openstreetmap.org/t/148767/34)); уточнить, из какого режима.
- [ ] Режим отображения всех объектов базы (линии и точки, которые редактор не рисует: indoor footway, члены отношений без геометрии и т. п.) — тонкими линиями поверх сцены, с фильтром по этажу и показом тегов, чтобы видеть общие узлы и примыкания.
- [ ] Режим визуализации истории изменений объекта (здания) по правкам с сервера OSM: версии (`/api/0.6/{type}/{id}/history`), кто и когда менял, changeset с комментарием, разница тегов и геометрии по шагам.

Манифест: id, версия API редактора, тип, лицензия, `allowedForEditing` (Esri, Яндекс — только показ). Включённые — настройка `simple3d:*` в профиле (до 255 символов: только id/URL).
  - Безопасность: токен OSM в localStorage (`osm/auth.ts`), CSP нет — модуль через `import()` прочтёт токен и сможет править от имени пользователя. Два уровня: декларативные (JSON: подложки, DEM, правила на тегах, пресеты, стили) — по любому URL; с кодом — только из официального списка после ревью, или в песочнице (Worker/iframe + postMessage, правки предлагаются, применяет редактор).
  - Готовность кода: фотосервисы — уже интерфейс `PhotoService` (`view/street-photos.ts`), нужен реестр; подложки — интерфейс `Imagery`, но константный `IMAGERY` (`view/basemaps.ts`); DEM — одна константа `DEM_URL` (`view/dem-tiles.ts`), от неё рельеф, отмывка и изолинии в main.ts — пересоздание на лету; валидатор — функции → `Issue[]` с явными вызовами и кэшем в main.ts, нужен реестр `rules[]` и сброс кэша (`setDeprecatedTags` — уже внешний список); инструменты — общего интерфейса нет (создание с колбэками в main.ts, цепочки `xTool.stop()`/`if (xTool.active)`): выделить `Tool` (start/stop/pointer/hint/правка в undo) — крупный рефакторинг, полезен и сам по себе.
  - Сделано (`src/plugins.ts`, `src/plugins/catalog.json`, вкладка «Плагины»): манифест, официальный список и свои по ссылке, подложки из плагинов на лету, реестр фотосервисов для модулей официального списка (`src/plugins/<module>.ts`, `activate(api)`). Осталось: Яндекс Панорамы первым плагином с кодом (проверить реестр фото вживую), кадастры WMS в каталог.
  - Порядок (исходный): 1) манифест, вкладка «Плагины», загрузка JSON; 2) декларативные подложки и кадастры; 3) реестр фотосервисов, Яндекс Панорамы первым плагином с кодом; 4) правила валидатора — декларативные, затем реестр; 5) сменный DEM по области; 6) интерфейс `Tool`.

## Известные риски

- Тайлы отстают от OSM (дни) → локальный оверлей отредактированных зданий.
- `/map` ограничен 0.25 deg² и 50k узлов; отношения могут прийти неполными.
- Противоречия `height` vs `building:levels` — не перезаписывать молча, предупреждать.
- `colour` бывает hex или CSS-именем — сохранять в исходном формате.
- Правки геометрии — минимальные: сложное (мультиполигоны, перенос узлов соседей, слияние)
  по-прежнему в iD/JOSM. Общие узлы с соседними зданиями двигать нельзя без явного подтверждения.
- Данные загружены только в пределах области редактирования: новые объекты и разрезы — только внутри неё.
