# OSM Simple 3D Editor — план

Браузерный редактор 3D-атрибутов зданий OSM (схема Simple 3D Buildings).
Без бэкенда, хостинг на GitHub Pages.

## Архитектура

- **Карта:** MapLibre GL + векторные тайлы OpenFreeMap (подложка; здания тайлов — только ниже z15 и пока не загружены свои).
- **Здания:** на z ≥ 15 — свои данные по тайлам z14 (`src/view/overpass-tiles.ts`): память (LRU) → IndexedDB
  (`src/view/tile-store.ts`, своя база на сервер) → сеть. Источник — OSM API `/map` того сервера, куда идёт запись
  (дробление на четверти при 400, неполные мультиполигоны — через `/full`), не больше двух запросов сразу (правила
  OSMF для API). Overpass с 2026-10-09 не используется (раньше — пул overpass-api.de / maps.mail.ru).
  Неполные ответы не кешируются; в индикаторе — источник и возраст тайлов, кнопка «Перезагрузить видимые тайлы».
- **Рендер:** three.js custom layer (`BuildingsLayer`), одна слитая геометрия на тайл, цвет и выделение в вершинах,
  крыши (в т.ч. straight skeleton в worker), плоские следы для контуров с частями и зданий нулевой высоты,
  оверлей поверх всего (`depthTest: false`) для подсветки выбираемого контура.
- **Правки:** единый режим — правки (`EditSession`) лежат поверх тайлов (оверлей подменяет объекты в тайлах),
  объекты начинают отслеживаться при первой правке. Можно создавать отношения `type=building` и менять их членов.
- **Геометрия и топология** (решение 2026-10-11): в OSM — простые замкнутые пути, связность — общими узлами,
  а не мультиполигонами из общих отрезков. Мультиполигон создаём только по необходимости: часть с дырами,
  контур здания из несвязанных частей. Чужие мультиполигоны и общие пути не перестраиваем и не «упрощаем» —
  правим, сохраняя их структуру (`restructureRing` в `src/edit/topology.ts`). Связность («ребро → чьё», «узел →
  чьи пути») строится в памяти из загруженных данных и служит всем инструментам (привязки, перемещение,
  вытягивание, разрезание, отделение от соседей). Почему не мультиполигоны: так принято в OSM (мультиполигон —
  когда путём не обойтись), пути без тегов в нескольких отношениях легко ломаются в iD/JOSM, каждая правка
  задевала бы много объектов; отделить часть от соседей на узлах — просто заменить общие узлы новыми.
  Части друг над другом с одним основанием — тоже два пути на одних узлах, без общего пути.
- **Запись:** OAuth 2.0 PKCE → свежие версии из API (`fetchElements`) → перенос правок (rebase тегов, слияние членов)
  → `changeset/create` → `upload` (osmChange `<create>`/`<modify>`) → `close`; записанное сразу попадает в кеш тайлов.
  Сервер по умолчанию — боевой, dev — по выбору.

   - Выбор и правка тегов частей — той же формой и той же сессией правок (undo/redo, список изменений),
     так что при возврате на карту правки сохраняются и отправляются вместе с остальными.
   - Дерево состава здания в панели: контур, части (с высотами), переход к части и скрытие отдельных частей,
     чтобы добраться до внутренних (полупрозрачность остальных или «показать только эту»).

## Известные риски

- Тайлы отстают от OSM (дни) → локальный оверлей отредактированных зданий.
- `/map` ограничен 0.25 deg² и 50k узлов; отношения могут прийти неполными.
- Противоречия `height` vs `building:levels` — не перезаписывать молча, предупреждать.
- `colour` бывает hex или CSS-именем — сохранять в исходном формате.
- Правки геометрии (этапы 7–10) — минимальные: сложное (мультиполигоны, перенос узлов соседей, слияние)
  по-прежнему в iD/JOSM. Общие узлы с соседними зданиями двигать нельзя без явного подтверждения.
- Данные загружены только в пределах области редактирования: новые объекты и разрезы — только внутри неё.
